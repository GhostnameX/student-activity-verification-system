- **ทางแก้:** (ก) ตรวจว่า local-part ของอีเมลตรงกับ studentId (ถ้ารูปแบบอีเมลมหาลัยเป็นแบบนั้น — ต้องเช็กกับผู้ใช้) หรือ (ข) import อีเมลเข้า roster ล่วงหน้าแล้วปิด bind flow หรือ (ค) ให้ staff อนุมัติการผูก หรือ (ง) OTP เบอร์โทร/อีเมลทางการ — ขนาด **S** (ก) / **M** (ค,ง) · ชนกับ Phase 2–5: ไม่ชน (แต่ต้องตัดสินใจก่อน deploy 0016)

### หมวด S — State machine / Transaction

ตรวจแล้วถูกต้อง: approve และ request-revision ใช้ `UPDATE … WHERE status='pending' RETURNING` ใน transaction (app.ts:754-770, 1043-1054) กดซ้ำ/พร้อมกันจะมีผู้ชนะ 1 คนอีกคนได้ 400; resubmit ใช้ guard เดียวกัน (1240-1252); การออกเลขคำร้อง/ใบรับรองเป็น `INSERT … ON CONFLICT DO NOTHING` + `UPDATE last_number+1 RETURNING` ใน transaction เดียวกัน (581-592, 775-788) พร้อม unique index บน `(year, number)` (schema.ts:109-114) → เลขไม่ซ้ำ และถ้า rollback เลขก็ไม่ถูกข้าม; flow ตรงกับ REQUIREMENTS ข้อ 2 และ 5 ยกเว้น S-1, S-2

#### S-1 · High · State machine — `reject` ไม่มีเงื่อนไข status ใน UPDATE และไม่ใช้ transaction → แย่งกับ approve แล้วทับสถานะ terminal ได้ — **แก้แล้วใน df2429c**
- **ปัญหา:** ตรวจ `pending` ด้วย SELECT แยก (app.ts:915-926) แล้ว UPDATE ด้วย `WHERE id = …` อย่างเดียว (app.ts:928-939) ถ้า approve commit คั่นระหว่างสองขั้นนี้ แถวจะกลับเป็น `rejected` ทั้งที่มี `certificate_number` และอีเมลใบรับรองถูกส่งไปแล้ว
- **ผลกระทบจริง:** admin 2 คน (หรือกดสองแท็บ) ในช่วงหน้าต่างเวลาสั้น ๆ → นักศึกษาได้ทั้งอีเมล "อนุมัติ+ใบรับรอง" และ "ไม่อนุมัติ" ข้อมูลสถานะขัด REQUIREMENTS ข้อ 2 (approved เป็น terminal); เลขใบรับรองถูกใช้ไปแล้วแต่คำร้องเป็น rejected
- **ทางแก้:** เติม `eq(requests.status,'pending')` ใน WHERE + ตรวจ `returning` (ถ้าว่างคืน 400) และห่อ audit/notify ให้เป็นแบบเดียวกับ approve — **S** · **ชน Phase 2** (Phase 2 แตะ route กลุ่มเดียวกัน) แก้ก่อนหรือพร้อมกัน
- **ความมั่นใจ:** ยืนยันแล้ว (จากโค้ด; ไม่ได้ reproduce race)

#### S-2 · Medium · State machine — `reject` เขียนทับ `requests.note` (หมายเหตุของนักศึกษา) ด้วยเหตุผลของ admin — **แก้แล้วใน df2429c**
- app.ts:932 (`note: body.reason ?? null`) — ถ้า admin ไม่ใส่เหตุผล note ของนักศึกษาจะกลายเป็น `null` ข้อมูลต้นฉบับหายถาวร (มี `rejection_reason` แยกอยู่แล้ว :933) · ทางแก้: ไม่แตะ `note` — **S** · ไม่ชน · ยืนยันแล้ว

#### S-3 · Low · State machine — `PATCH /api/requests/:id` เช็ก pending แบบไม่ atomic และไม่จำกัดความยาวข้อความ
- app.ts:705-717 (UPDATE ไม่มี `status='pending'`) → นักศึกษาแก้ note หลัง approve ได้ถ้าชนจังหวะ; `note`/`reason` เป็น `t.String()` ไม่จำกัดความยาว (app.ts:668,722,983) · ทางแก้: ใส่ guard ใน WHERE + `maxLength` — **S** · ยืนยันแล้ว (โค้ด)

#### S-4 · Low · ข้อมูล — ไม่มี unique `(request_id, slot)` และไม่มี CHECK slot ∈ {1,2} ใน DB
- schema.ts:134-152; ยืนยันกับ `ua_dev` (index มีแค่ pkey + `attachments_request_idx`) → resubmit สอง request พร้อมกันที่สร้าง slot ที่ยังไม่มี (app.ts:1161-1184) ทำให้ slot ซ้ำได้ ส่วนความถูกต้องของ slot พึ่งโค้ดอย่างเดียว · ทางแก้: unique index + CHECK (migration ใหม่ ไม่ใช่ ADD COLUMN) — **S** · ไม่ชน แต่ต้องนับรวมในแผน migration · ยืนยันแล้ว

#### S-5 · Medium · State machine/Audit — audit log และ notification เขียนหลัง commit นอก transaction และกลืน error
- app.ts:158-187 (`.catch(console.log)`), 843-862, 1069-1078 → คำร้องถูกอนุมัติแล้วแต่ไม่มี audit row ได้ ขัดเจตนา REQUIREMENTS ข้อ 5 และไม่สม่ำเสมอกับ roster ที่เขียน audit ใน transaction และไม่กลืน error (roster.ts:282-301) · Phase 2 ต้องเขียน audit `staff_check` + notification — **ควรตัดสินใจรูปแบบเดียวก่อนเริ่ม** · ทางแก้: ย้าย audit เข้า tx — **M** · ชน Phase 2 · ยืนยันแล้ว

#### S-6 · Medium · คุณภาพ — ไม่มีเทสต์อัตโนมัติสำหรับ route คำร้อง (approve/reject/revision/resubmit/สิทธิ์)
- เทสต์ที่รันได้: db-guard, oauth-security, roster, certificate-format; ส่วน `gate-smoke.ts` เป็น manual และ mutate DB/Storage ที่ตั้งค่าไว้ (PREDEPLOY-AUDIT-STATUS.md ข้อ 9) ⇒ S-1 ไม่มีอะไรจับ · ทางแก้: เพิ่ม integration test บน `ua_roster_test` (คำร้อง × role matrix + race) ก่อนแตะ Phase 2 — **M** · ชน Phase 2 (ควรทำก่อน)

### หมวด F — ไฟล์แนบ

ตรวจแล้วถูกต้อง: ตรวจ MIME ที่ประกาศ + magic bytes (PNG/JPEG/WebP/GIF/PDF) + ขนาด ≤ 5MB ฝั่ง server (app.ts:36-67, 230-253); ชื่อ object ที่เก็บเป็น `requests/<uuid>.<ext>` ที่ server สร้างเอง → **path traversal ไม่ได้** (app.ts:257); ownership: ทุก upload ลงตาราง `attachment_uploads` และใช้ได้ครั้งเดียวต่อเจ้าของ (app.ts:283-289, 605-622, 1141-1158); `fileName/fileType/fileSize` ที่ client ส่งตอนสร้างคำร้องถูกเมินและใช้ค่าจาก ledger แทน; slot ≥ 3 สร้างไม่ได้ (app.ts:563)

#### F-1 · Medium · ไฟล์แนบ — ไม่มี quota/rate limit ต่อนักศึกษา, ไม่มีงานลบไฟล์ที่อัปโหลดแล้วไม่ถูกใช้, ไม่จำกัด body ก่อนตรวจขนาด
- **หลักฐาน:** app.ts:204-314 (นักศึกษาอัปโหลดกี่ครั้งก็ได้), ledger `consumed_at IS NULL` ไม่มีใครลบทั้งแถวและ object ใน Storage (ไม่มี job ใน repo), `app.listen` ไม่ตั้ง `maxRequestBodySize` (index.ts:3-6 → ค่าเริ่มต้นของ Bun 128MB) ขณะที่ตรวจ 5MB หลังอ่าน body ทั้งก้อน (app.ts:234-239)
- **ผลกระทบจริง:** นักศึกษาคนเดียวทำให้ Storage เต็ม/เสียค่าใช้จ่าย หรือกิน RAM Render (512MB) ด้วย request ใหญ่ — ปัจจุบัน Storage มี 19 object (3.1MB) จึงยังไม่เห็นผล
- **ทางแก้:** `maxRequestBodySize` ~6MB, จำกัดจำนวน upload ที่ยังไม่ consume ต่อ student, cron ลบ upload ค้าง >24 ชม. (ต้องได้รับอนุมัติเพราะเกี่ยวกับ object ใน bucket) — **M** · ไม่ชน Phase 2–5 · ความมั่นใจ: ยืนยันแล้ว (โค้ด)

#### F-2 · Low · ไฟล์แนบ — avatar ตรวจแค่ MIME ที่ประกาศ (ไม่มี magic bytes) แล้วเก็บใน bucket สาธารณะ; ลบรูปเก่าก่อนอัปโหลดใหม่
- app.ts:1385-1401 (ต่างจาก `/api/upload` ที่ตรวจ magic bytes), 1416-1430 (ลบก่อนแล้วค่อยอัปโหลด; ถ้าอัปโหลดล้มเหลวรูปเดิมหาย) · ทางแก้: ใช้ `detectAllowedUploadFileType` ซ้ำ + สลับลำดับ — **S** · ยืนยันแล้ว

#### F-3 · Low · ไฟล์แนบ — `fileName` จาก client เก็บตรง ๆ ไม่จำกัดความยาว
- app.ts:226,283-289 → ใช้แสดงผลเท่านั้น (Svelte escape ให้) ไม่กระทบ path; แนะนำตัดความยาว/ตัวอักษรควบคุม — **S** · ยืนยันแล้ว

#### E-1 · High · อีเมล — `EMAIL_FROM` ที่ใช้จริงคือ `onboarding@resend.dev` (ผู้ส่งทดสอบของ Resend)

- **ความมั่นใจ:** น่าจะเป็น / **ต้องเช็กบน production**: (1) Render → Environment → ค่า `EMAIL_FROM` จริง (render.yaml อาจไม่ได้ถูกใช้ ดู G-1), (2) Resend → Domains ว่ามีโดเมน verified ไหม, (3) Render logs ค้นข้อความ `[email] send failed:` (Resend จะตอบ 403/422), (4) Resend → Emails/Logs ดูสถานะการส่งของใบรับรองที่อนุมัติไปแล้ว

- **หลักฐาน:** `sendStatusEmail` พิมพ์ความล้มเหลวลง console เท่านั้น (app.ts:147-155); ใบรับรอง+อีเมลของ approve ทำใน `setImmediate` หลัง response (app.ts:864-896) — ถ้า process รีสตาร์ท/error คั่นกลางงานนั้นหายเงียบ ๆ; ค้นไม่พบ route สร้าง/ส่ง PDF ซ้ำ (มีที่เดียวคือใน approve); ถ้าสร้าง PDF พลาด ระบบยังส่งอีเมลที่เขียนว่า "กรุณาตรวจสอบใบรับรองที่แนบมาด้วย" โดยไม่มีไฟล์แนบ (app.ts:126-128, 889-894); กรณี reject ส่งอีเมลแบบ `await` ในคำขอเดียวกันและไม่มี timeout (970-977)
